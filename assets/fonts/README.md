# assets/fonts

HUD 的像素字体（E6.2），由引擎读取，所有游戏共用（`docs/architecture.md` 第 18 节「文字和图片」）。和 `assets/art` 一样，`.aseprite` 是二进制源文件（走 Git LFS），这份 README 是它的文本说明：**改字形之前先读这里**，改完同步更新。

| 文件 | 说明 |
|---|---|
| `loom_5x7.aseprite` | 源文件：96×48，RGB，1 帧，没有 tag |
| `loom_5x7.png` | 导出的图，96×48，RGBA PNG（走 LFS） |
| `loom_5x7.json` | 导出的数据，json-array 格式 |

引擎启动时读 `assets/fonts/loom_5x7.json`，路径相对工作目录，也就是仓库根目录。`loom run`（包括 `--no-hud`）和 `loom serve` 都读，文件缺失或尺寸不是 96×48 都会报错退出（`the HUD font assets/fonts/loom_5x7.json: …`）。`loom view` 不读。

## 布局

- 图是 96×48，分成 16 列 × 6 行的格子，每格 6×8；
- 字形占每格左上角的 5×7，右边一列、下面一行留空，作为字距和行距；
- 字形像素是不透明白色 `#ffffff`，其余全透明。引擎画字时把白色乘上文字的颜色，alpha 小于 0.5 的像素丢掉，所以边缘是硬的；
- 覆盖可见 ASCII 32 到 126，共 95 个字符。最后一格（127）空着。

字符码 `c` 到格子的公式（`loom_core::hud::glyph_cell`）：

```
i   = c - 32
col = i % 16
row = i / 16            -- 整数除法
格子左上角 = (6 * col, 8 * row)
字形矩形   = (6 * col, 8 * row, 5, 7)
```

例如 `A`（65）：i = 33，第 1 列、第 2 行，字形在 (6, 16)。32 到 126 以外的字符（包括中文和 `é`）都画成 `?`（63，第 15 列、第 1 行）。

文字宽度：n 个字、放大 `scale` 倍，宽 `(6n - 1) · scale`（`loom_core::hud::text_width`），最后一个字不算右边的空列。

## 容易混的字形

5×7 的格子很小，下面几组靠这些特征区分：

| 字 | 特征 |
|---|---|
| `0` / `O` | `0` 有一道从左下到右上的斜杠；`O` 是空心的圆角框，里面没有东西 |
| `1` / `l` / `I` | `1` 左上有一个斜着的旗，底下是 3 格宽的底座；`l` 顶上是往左伸的 2 格短横，底下是 3 格宽的底座；`I` 上下两道横一样宽，都是 3 格，是对称的 |
| `5` / `S` | `5` 顶上是满宽 5 格的直横，左上是直角，左边一道竖往下接中间的横；`S` 顶上只有右边 4 格，左上缺角成圆弧，中间的横也缩进一格，底下的横缺右下角 |

字形都是手画的，原则是在原始尺寸下也能一眼认出来。数字 `0` 到 `9` 用得最多（瓶数、魂数），每个都要和字母分得开。

## 怎么画出来的

aseprite 的 MCP 的画布根目录是 `assets/`（2026-09-27 起），路径都带 `fonts/` 前缀，直接在这里画：

1. `create_sprite`：`file: "fonts/loom_5x7.aseprite"`，`width: 96`，`height: 48`，`color_mode: "rgb"`，不传 `palette`。已有同名文件时加 `overwrite: true`。
2. `run_lua`：`file: "fonts/loom_5x7.aseprite"`，代码见下文。
3. `preview` 看一遍，例如 `scale: 8`、`background: "black"`，确认每个字形都清楚。
4. `export_sheet`，参数见下文「怎么重新导出」。

E6.2 时画布根目录还是 `assets/art`，字体是在那里画完再搬过来的；JSON 里的 `meta.image` 是相对文件名，所以搬动不影响。

要改已有的字形：直接对 `fonts/loom_5x7.aseprite` 跑 `run_lua` 再导出；也可以改下面 Lua 里的字符串，按上面 4 步从零重建。

Lua 里的像素写成字符串，整张 96×48 的图一行一个字符串，`#` 是白色，`.` 是透明，所以重建的结果完全确定。E6.2 核对过：按这几步重建再导出，得到的 PNG 和 JSON 与仓库里的逐字节相同。

## 怎么重新导出

aseprite 的 MCP `export_sheet`：

```
file: "fonts/loom_5x7.aseprite"
png: "fonts/loom_5x7.png"
data: "fonts/loom_5x7.json"
data_format: "json-array"
```

导出后检查 `loom_5x7.json`：
- `frames` 只有 1 项，96×48，`trimmed` 是 false；
- `meta.image` 是相对文件名 `"loom_5x7.png"`，不能是绝对路径；
- `meta.format` 是 `RGBA8888`；
- `meta.size` 是 96×48（引擎会检查，不对就报 `the image is WxH, but the glyph layout needs 96x48`）；
- `meta.frameTags` 是空的：引擎按上面的公式找字形，不用 tag。

改完跑 `cargo test -p loom_engine project_hud_font_has_every_glyph_in_its_cell_top_left`。它会检查：除空格外每个字都有像素；有像素的地方都是不透明白色，而且都在各自格子的 5×7 里；`A` 的顶行是 `.###.`。
